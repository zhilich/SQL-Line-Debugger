# SQL Line Debugger architecture

The Windows Forms application targets .NET 8 on Windows x64. Each debug session starts a separate instance of the executable as a hidden MTA native worker; Forms runs on an STA thread with a message pump. Two named pipes restricted to the current Windows user carry commands and snapshots separately. UI commands enter a channel and are written asynchronously. A fresh worker process avoids the LocalDB registration problem observed when restarting after cancellation under the same process ID, and isolates native ABI failures from the UI. The small C++ DLL hosts native COM callback vtables and queues copied events for a dedicated managed reader. The SQL procedures and functions execute intact inside SQL Server: this application does not interpret SQL, rewrite modules, inject instrumentation, or replay prior statements.

## Execution

1. The worker process opens a control connection with pooling disabled, before registration. It requests the marshaled server interface using `master.dbo.sp_enable_sql_debug`.
2. `CoUnmarshalInterface` obtains `IHostDebugServerInstance`; the native bridge registers this application's machine and process ID.
3. A new target connection matches that registration. Its batch generates `PushDynamic`; an initial asynchronous break starts statement events.
4. `Push` identifies stored modules by database and object ID. The control connection retrieves their actual `sys.sql_modules.definition`. `PushDynamic` supplies dynamic batch text directly.
5. `Step` supplies statement spans and scope. The bridge obtains scalar locals with `GetSyms`, copies values to JSON, frees COM allocations, enqueues the event, and returns the RPC. The managed event pump reads the queue and applies the pause policy outside the callback.
6. A pause raises an immutable snapshot to the UI and returns the COM callback immediately, leaving SQL Server waiting for its next command. Resume calls the native Continue export from the worker's command reader in the MTA COM apartment. This avoids holding a callback RPC open during a long human pause. The UI stays responsive.
7. The target's ordinary `SqlDataReader` collects result sets and `InfoMessage` collects PRINT/SQL informational output. Results are available as the server produces them. A grid displays up to 10,000 rows per result set; remaining rows are drained.
8. Stop sends SQL client cancellation on a separate thread and resumes a paused worker so SQL Server can consume the attention. Calling `StopDebugging` inside the callback means detach rather than cancellation. LocalDB cancellation can affect subsequent registrations for the same process, so each run uses a fresh worker process. Registration is removed after target execution closes; demo fixtures are dropped afterward. The worker exits when the run ends. Host disconnection requests cancellation.

## Source mapping

The `m_offStart` and `m_offEnd` values are UTF-16 byte offsets. On the tested engine, the end identifies the final character inclusively, often omitting a semicolon, and spans can include following whitespace. `SourceDocument` preserves the original database or callback text. Offset validation rejects odd, inverted, or out-of-range spans instead of guessing a line. The RichTextBox displays normalized line endings; prefix conversion maps original coordinates to display coordinates without replacing the underlying source.

Breakpoints bind to a database/object key, a SHA-256 hash of exact source, and a line. Dynamic SQL keys include its text hash. Query breakpoints bind to the actual submitted batch. A breakpoint on a continuation line binds to that statement; trailing indentation on the next line is excluded. If a module's definition changes between loading and execution, an old hash cannot bind to the new definition. Modules should not be concurrently altered during a debug run: the private API does not provide a verified execution-version source snapshot.

Continue, Step Over, and Step Out are managed policies over native Step Into events. Continue stops at matching breakpoints; Over also stops when the call depth returns to the original depth; Out stops at a shallower depth. The initial event and explicit Pause stop at the next statement boundary. This keeps breakpoints effective in nested functions/procedures at the cost of server round trips during Continue. A long executing SQL statement cannot be paused in its interior.

## Compatibility boundary

This is a real, experimental native debugger built on private SQL Server COM interfaces, with Windows authentication, one active target connection, and serial T-SQL execution. SQL CLR and parallel UDF execution are not supported. Workers and stack frames carry batch/worker/level identifiers, but concurrent-worker behavior is not validated. Table-variable symbols remain leaves; TempDB inspection instead uses XE ownership/mapping evidence and an embedded SQL batch derived from the raw-page reader. Its storage formats and limits are documented in README.md.

The SQL debugging COM proxy must already be installed and registered on the workstation (on the test machine it came with the SQL debugging/SSDT components). The app does not call the SSDT debugger engine. It requires sysadmin access for native registration. TempDB inspection creates an owned server XE session and executes its page-reader SQL directly against `tempdb`; it does not install a procedure or modify firewall settings. Command cancellation does not undo SQL effects already committed before Stop.

## TempDB discovery and snapshots

The worker opens an observer connection before native registration and creates a SPID-filtered XE session before running the user batch. Background collection orders `lock_acquired`, `module_start`/`end`, `sp_statement_starting`/`completed`, and `sql_statement_starting`/`completed` by event sequence. Module events omit statement payloads. OBJECT locks provide signed object IDs (including negative table-variable IDs); associated HOBT/partition/allocation IDs are resolved against TempDB metadata. Only objects observed in the target session's lock stream enter the list. Local objects additionally need an active owning native frame; unknown ownership is pending evidence, not session-wide lifetime. Global tables may have no native owner. Internal metadata names and creation dates distinguish dropped/replaced objects; native scope generations distinguish repeated calls, nesting, and shadowing.

Statement/object sets form name constraints. A single variable with a single physical object resolves immediately after statement completion; multi-variable statements retain internal names until additional constraints determine a one-to-one mapping. SQL tokenization excludes literals, comments, quoted identifiers, and scalar-only references. Completed events restore caller statement context after nested calls. Buffer loss discards incomplete statement context and pending constraints while preserving confirmed names for live object identities and native frame invocations. Metadata changes and frame retirement invalidate those confirmed mappings.

Procedure entry/exit may acquire locks on cached storage while the caller's EXEC is the only available statement context. EXEC alone does not establish ownership or name constraints. Pre-entry object locks are grouped under their enclosing statement, then bound to the new native invocation by module_start. If the enclosing statement was lost, only immediately preceding unowned locks within 20 milliseconds of module_start are eligible. Each native invocation is matched once, including recursion; binding can wait for a delayed native source push. This establishes lifetime without guessing variable names, making empty unresolved variables inspectable at the first procedure statement. Later references resolve their names normally. Module return discards initialization candidates, and native frame exit removes their visibility. Cache renames between internal hex and padded user names preserve ownership when object ID and creation date remain the same. A local object can also acquire ownership from an actual table reference after event loss. Cached metadata and cleanup locks after return cannot publish unowned local objects as unresolved caller variables.

XE DMV reads can wait for buffer dispatch. They run outside the short state lock used by native callbacks, so pauses do not wait for collection. Immutable object lists accompany pause notifications and later discovery messages carry pause IDs; the host ignores messages for earlier pauses. Collections never execute the row reader. The UI shows name, Inspect, and Global, preserving selection and descending last-lock order as names resolve.

Inspect opens a modal snapshot dialog and asynchronously executes the embedded `SelectTempDbRows.sql` batch in the host process using an independent autocommit connection to `tempdb`. The target remains paused until the dialog closes. The exact object ID, internal name, and creation date are checked before reading. Rows, types, duplicates, NULLs and binary values are retained in a detached DataTable; large SQL decimals use SqlDecimal. Money/smallmoney decode signed little-endian 8/4-byte row values through exact decimal division by 10,000, including the minimum signed value; the final projection uses the original SQL monetary type. There is no auto-refresh. Reader errors appear in the dialog; closing during a read cancels that inspection. The supplied physical-page reader and its unsupported formats remain a separate compatibility boundary from native stepping.

Global uses that same embedded batch with an optional global-name parameter. The complete physical snapshot is decoded before replacing the destination; its typed projection is materialized with SELECT INTO inside SQL Server, avoiding CLR decimal conversion. Drop and creation run in separate dynamic batches within one transaction; a failed materialization rolls back the replacement. Names are validated and quoted as a single identifier. GlobalTempTableCopies retains each successful creator connection for the form's lifetime, including after the source debug session ends. Failed/cancelled attempts close only their new connection. The modal name dialog keeps the target paused, supports cancellation, and shows validation/SQL errors in place.

The installed SQL Debugging 130 COM proxy expects a `Ping` method after `OnMatch` on the match interface. That slot is missing from the historical published definition. The original bridge omitted it: RPC dispatched through adjacent RTTI data, raised an execute access violation, and Windows Error Reporting suspended the worker for roughly 20–23 seconds while collecting a report. RPC later recovered, so the previous correctness test passed despite the delay. Adding the slot fixes the wait and the subsequent unregister `0x80070057` diagnostic. The UI regression now requires every demo step to arrive within 2 seconds; measured times after the fix are milliseconds. The native suite also holds a pause for 30 seconds to exercise heartbeat calls. Private interfaces still require validation on other installed proxy/server versions.
